# 站内通知中心

通知直接保存在 Backend 的业务数据库中，RabbitMQ 负责跨实例刷新提醒，浏览器通过 SSE 收到提醒后查询 HTTP API。当前没有接入邀请、任务或数据源等生产业务事件，启用后列表初始为空。

## 保存通知

业务事件适配器在自己的事务中调用 NotificationWriter.writeRequired。该方法强制要求已有事务，直接写入接收者的通知、收件箱序号及事件去重元数据，返回时通知已经写入当前事务。业务提交后即可查询，业务失败则全部回滚，保存通知不依赖 MQ。

事件标识只能对应相同的规范化内容。notification_events 只保存标识、空间、摘要和时间，用于阻止重复调用再次生成通知，不保存待执行任务或正文。通知接收者在写入时按当前成员资格筛选，机器主体不接收个人通知；即使调用方事务已建立旧的可重复读快照，也通过当前读检查成员关系。

单次最多一千名接收者，按主体排序后锁定收件箱，避免跨空间并发时以不同顺序取锁。每个用户的序号与通知在业务事务内共同提交，用于固定分页范围与全部已读边界。并发事件按数据库提交的收件箱序号展示，不以 MQ 到达顺序决定通知顺序。

## MQ 刷新提醒

每次新通知或已读状态变更，都在相同事务中递增收件箱 revision 并设置 signal_pending。后台只扫描已提交的待发布标记，使用短租约领取，将接收者与版本广播到 RabbitMQ。消息不包含正文、标题、空间名称或未读数。

发布使用持久化消息、mandatory 路由检查与 Publisher Confirm。只有确认成功后才清除对应版本的待发布状态；期间如果有更新版本提交，标记继续保留。MQ 不可用、发布后确认丢失或进程退出时，租约到期后重试。这里的数据库补偿只负责刷新提醒，不存在异步生成通知的任务队列。

每个 Backend 实例使用自己的持久化 Quorum 广播队列，队列启用单活消费者。必须配置唯一且重启后稳定的 NOTIFICATIONS_INSTANCE_ID；默认 backend 仅适用于单实例。多个副本使用相同标识会共用同一个队列，不能据此实现广播。消费者失败后，消息经本实例的十秒 Quorum 延迟队列重投，不会重新广播给其他实例。主队列与重试队列均启用至少一次死信转发，目标暂不可用时保留消息。

已声明的队列在实例断线后保留消息，消费者使用相同标识重新连接后继续接收。实例永久下线时，维护者应在核对后清理其主队列与重试队列；不要用随机实例标识反复创建持久化队列。新实例首次声明队列之前的历史提醒不回放，浏览器建立连接后会查询数据库补齐状态。单个 Broker 的持久化不等于多节点高可用，应保留其数据卷并按部署需求配置集群。

MQ 消费确认表示该实例已接纳刷新提醒，不代表浏览器已经看到通知。SSE 只发送固定 refresh 信号，重复或乱序提醒都触发 HTTP 最新状态查询，不直接覆盖浏览器的未读数或通知内容。浏览器每三十秒、恢复焦点或重新可见时也会补查。消息传输是至少一次处理，浏览器展示最终以数据库查询结果为准。

通知功能不再使用 Redis Pub/Sub。项目中的 Redis 继续承担既有 Gateway Session 和外部 API 限流职责，与通知刷新投递无关。

## HTTP、已读与权限

HTTP 提供当前用户的状态、分页和详情查询，以及单条已读和全部已读。没有公开创建通知或查询任意接收者的接口。浏览器继续使用 Gateway Session Cookie，写请求需要 CSRF；Backend 独立校验 JWT 与用户身份。

列表、详情、未读数及已读操作均限定接收者与当前 Workspace 成员关系。被移出空间后不能继续读取该空间的通知；重新加入后，保留期内已有历史通知可以重新可见。相同旧事件不会因为成员重新加入而再次生成通知。

查询 state.latestSequence 后，用 upToSequence 固定分页范围。全部已读必须提交客户端所见 throughSequence，仅更新其范围内仍可访问的通知，之后到达的新通知继续未读。单条已读幂等，状态变更也通过 MQ 提醒其他实例与标签页。

通知目标仅允许已知站内资源类型和资源 ID，不保存任意跳转 URL。打开前重新检查通知资格，目标页面继续校验实际资源权限和存在性。正文和标题按普通文本展示，前端内存随账号退出或切换清空，不保存到 IndexedDB。

SSE 每十五秒心跳，每次连接最多五十五秒且不超过 JWT 有效期。默认每节点最多五百个连接、每用户每节点最多五个，超限返回 429；推送任务使用有界队列。Nginx 对准确的流路径关闭缓冲和压缩，Gateway 为该路径保留独立超时设置，错误响应仍返回正确的 JSON 403、404 或 429。

## 事件接入与保留

事件适配器负责业务触发条件、接收者和内容，完成原业务授权后，在事务结束前调用直接写入入口。事件标识、发生时间、接收者快照与内容在重试中应保持稳定；超过一千名接收者时，在事务中拆分为多个稳定标识的命令。

命令允许最多七天前的事件及五分钟的未来时钟偏差，过旧请求不能通过重新生成标识绕过业务约束。通知与去重元数据默认保留九十天，可配置八至三百六十五天；分批清理不会重置收件箱序号。实例与 MySQL 应使用一致的时区约定，备份继续按敏感业务数据保护。

站内通知和邮件是独立通道。保存站内通知不调用 Resend，也不复用邮件投递状态；邮件服务自己的可靠异步投递链路保持独立。通知偏好、摘要合并、浏览器系统通知和具体业务事件按后续需求逐项接入。

## 新建、升级与回退

功能默认关闭。新建 Compose 环境依次执行 [通知建表](../backend/src/main/resources/db/migrate-notifications.sql) 和 [直写升级](../backend/src/main/resources/db/migrate-notifications-direct.sql)。新建库不创建旧的通知生成 Outbox。

已有旧版本部署应先备份业务库，暂停新的通知写入，让旧通知消费者排空 PENDING/PUBLISHED 任务，再停止所有旧实例。随后执行两份 SQL，部署配套应用和代理配置，设置唯一稳定的 NOTIFICATIONS_INSTANCE_ID，再启用 NOTIFICATIONS_ENABLED 及 RabbitMQ 监听。升级脚本发现未完成旧任务时会拒绝继续，不能通过直接删除旧任务或重启来绕过。

升级保留通知、已读状态、收件箱序号及旧事件去重信息；旧 notification_outbox 表原样保留用于核对，运行时不再读取它。重复执行不会覆盖新版本的提醒租约。旧 Broker 的生成队列及交换机不被新代码使用，排空并核对后可由维护者单独清理，禁止混跑两种版本。

连接上限和保留期配置继续沿用示例文件，无新增 Secret 或独立服务。公共 HTTP 契约与 SDK 仍为 5.2.0。TypeScript SDK 提供普通 HTTP 调用，浏览器适配层使用 EventSource；生成的 Python SSE 方法是完整文本响应，并非增量流式订阅工具，机器身份不能访问个人通知中心。

回退前关闭通知写入与广播，保留现有通知、事件元数据和序号；旧应用不理解新的直接写入入口和待发布标记，不能仅回退镜像就恢复旧生成流程。验证结果与待办统一见 [项目状态](STATUS.md)。
