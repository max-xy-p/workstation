# 笔记版本历史、差异与恢复

## 版本如何产生

MySQL 保存当前笔记及已经提交的历史快照。浏览器本地输入和 IndexedDB 草稿不会增加服务端版本；创建、导入或成功更新才会产生持久化结果。普通更新继续使用 `expectedVersion` 检查并发冲突，失败时不增加版本，也不留下历史。

历史记录保存完整标题和 Markdown 正文。普通保存只有在标题或正文不同于最近一份快照时才追加历史；仅修改标签、文件夹、项目或重复保存相同内容，仍沿用原有持久化版本递增规则。因此历史中的笔记版本号可以有间隔。A 改成 B 再改回 A 会保留三次内容状态。手动保存和自动保存统一标为“编辑”。

历史记录 ID 用于定位快照，对应的笔记版本号表示这份内容在哪次持久化时产生，两者含义不同。显式恢复始终生成新版本及“恢复”记录，即使恢复内容与当前相同，也保留这次操作及来源。

## 查看和比较

在已有笔记工具栏打开“版本历史”，选择一条记录，可查看原文或差异。桌面同时展示历史列表与内容，窄屏使用“历史列表”“预览”“差异对比”切换。

打开抽屉时读取一份服务端笔记，历史分页以该版本作为上界。期间新增历史不会挤动当前分页；点击“刷新历史”才纳入新记录。默认比较选中历史与这份已保存内容，也可切换为当前编辑内容，包含尚未保存的修改。浏览、翻页和切换比较对象不会写回编辑器。

标题单独比较，Markdown 正文按行比较，保留空白、缩进及换行差异。比较在浏览器 Worker 内完成，文本不会发送给其他比较服务，也不会作为 HTML 执行。

两侧正文各不超过 200,000 个 JavaScript 字符串长度单位及 5,000 行时尝试高亮；超过边界、比较复杂、等待超过 1 秒或 Worker 不可用时，提供原文预览。原文每段约 12,000 个长度单位，并保护 UTF-16 字符边界。这些限制只影响展示，不改变原有保存容量；降级后仍可恢复历史。

## 恢复与草稿保护

选择记录后点击“恢复此历史”，核对内容并再次确认。恢复只替换标题和正文，保留恢复当时的文件夹、项目、标签和任务依据关联。例如当前 v12 恢复 v8，成功后成为 v13，原历史继续保留。

当前有未保存修改时，“保留草稿并恢复”会先确认修改已写入 IndexedDB，再提交恢复。缓存失败会中止恢复。成功后编辑器启用新编辑会话，原草稿保留在原会话下，可从草稿入口找回；后续保存不会覆盖这份保留的草稿。浏览器草稿仍需依靠当前浏览器存储，不能替代数据库备份。

提交恢复期间暂停自动保存并阻止重复提交、关闭和导航。恢复携带比较时的服务端版本；他人已修改笔记会返回冲突，保留当前输入及草稿。请求失败或响应丢失时，应先刷新历史核对服务端状态，再决定是否重新比较和恢复，不能把失败响应当成恢复成功。

普通保存、历史恢复、历史快照和审计写入在同一服务端事务中完成。接口使用及响应结构以 [OpenAPI 契约](openapi.md) 为准。当前不提供自动三方合并。

## 共享和保留边界

具有 `NOTE_READ` 的成员，包括只读成员，可查看该笔记的全部保留历史，也能看到后来从正文删除的文字。历史属于共享笔记，不是作者私人草稿。恢复需要 `NOTE_WRITE`；作者和来源由服务端决定，迁移基线不推测作者。

历史按 Workspace 和笔记隔离。移入回收站后保留历史，但需先从回收站恢复笔记，才可查看或恢复历史正文。永久删除笔记会连同历史快照删除，审计不会另存正文副本。

当前保留全部快照，不提供逐条删除、自动压缩或过期清理。普通连续相同内容会去重，自动保存仍可能使历史持续增长；容量观察和数据库备份应覆盖历史表。

## 升级与回退

新安装与升级共用 `backend/src/main/resources/db/migrate-note-revisions.sql`。首次初始化按基础结构、项目数据源、笔记历史的顺序执行，开发和生产 Compose 均已挂载；已有数据卷不会自动重跑初始化。部署总体流程见 [CI/CD 与部署](ci-cd.md)。

已有数据库需先具备当前 Workspace、笔记版本及回收站结构。升级步骤如下：

1. 安排维护窗口，暂停全部旧应用写入，备份数据库并确认可恢复。
2. 对目标业务库执行历史迁移，确认表结构及基线完整。脚本默认使用 `workstation`，自定义库名需核对实际执行目标。
3. 为活动笔记和回收站笔记各记录当前内容的 `BASELINE`；作者为空，时间为迁移时刻，不改变现有 `notes.version`。迁移无法补回过去从未存档的内容。
4. 部署配套 Backend、Frontend 和 SDK，验证后恢复写入。禁止混用新旧 Backend 写入，以免旧实例绕过历史维护。

迁移可重复执行，同一笔记同一版本不会重复补基线。回退应用时保留历史表；旧应用运行期间不会完整记录内容变化。重新升级时再次暂停写入并执行迁移，为当前版本补齐基线，明确这段期间的历史缺口。需要恢复升级前的完整状态时，使用维护窗口前的数据库备份；仅回退镜像不会撤销数据变化。
