# Agent 执行流程

对于一般代码任务，遵循以下流程：

```text
理解需求
    ↓
阅读相关文档与现有实现
    ↓
确认模块职责、数据真源和契约
    ↓
设计最小范围修改
    ↓
实现代码
    ↓
补充或更新相关测试
    ↓
运行受影响模块的编译与测试
    ↓
涉及 Backend 或 Gateway 的代码、测试或构建配置时，检查两模块综合覆盖率是否达到 80%
    ↓
通过 SonarQube MCP 检查当前修改
    ↓
修复当前修改引入的 Sonar Issue
    ↓
源码或测试再次修改后，重新执行受影响的验证和覆盖率检查
    ↓
更新受影响文档
    ↓
汇报实际修改和实际验证结果
```

修改 Backend 或 Gateway 的代码、测试或构建配置后，Agent 必须在最后一次相关修改之后分别运行两个模块的 `clean verify` 生成新报告，再从仓库根目录亲自运行 `python scripts/check_java_coverage.py`。脚本按两个模块 JaCoCo 的行与分支计数计算综合覆盖率；低于 80% 时补充有业务价值的测试并重新验证。最终回复必须写明两次构建、检查命令的执行结果和实际综合覆盖率。无法运行或检查失败时，说明原因和未完成的验证，不得使用旧报告声称达标或将任务报告为完成。Frontend、SDK 与脚本不纳入此指标；云端 SonarQube 的新代码覆盖率和 Quality Gate 仍需分别核对。

对于 OpenAPI 变化：

```text
修改 OpenAPI
    ↓
检查契约兼容性
    ↓
重新生成客户端
    ↓
修改 Backend
    ↓
修改调用方
    ↓
检查 SDK 版本
    ↓
运行相关测试和构建
    ↓
检查 SonarQube
```

对于数据库变化：

```text
确认现有 Schema 和历史数据
    ↓
设计迁移
    ↓
修改 Entity / Mapper / Service
    ↓
补充迁移脚本
    ↓
补充测试
    ↓
验证已有数据卷升级路径
```

对于认证或授权变化：

```text
确认浏览器和机器调用两条认证链路
    ↓
确认 Gateway 职责
    ↓
确认 Backend 独立授权边界
    ↓
检查 CSRF / Bearer Token 行为
    ↓
补充拒绝与成功场景测试
    ↓
检查日志和错误信息是否泄露敏感数据
```

## Agent 完成任务时的输出要求

完成任务后应简洁说明：

1. 修改了什么；
2. 为什么这样修改；
3. 修改涉及哪些主要文件；
4. 实际执行了哪些验证；
5. 测试、构建和 SonarQube 检查结果；
6. 是否存在未完成验证、已知风险或后续事项。

不得：

- 声称执行了实际没有执行的命令；
- 声称 SonarQube 通过但实际没有完成分析；
- 隐瞒测试失败；
- 隐瞒无法访问的外部服务；
- 把历史问题描述成本次修改导致的问题；
- 为了让结果看起来成功而关闭、跳过或放宽检查。
