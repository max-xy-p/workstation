# Workstation 下一阶段功能实施方案

> 编写依据：2026-09-22 仓库现状。本文件是待实施方案；实际进度与验证结果只维护在 `docs/STATUS.md`。

## 1. 目标与边界

让用户在一个 Workspace 内协作整理 Markdown 笔记、项目资料和任务，并能从项目追溯“为什么做、依据是什么、做到哪里”。先解决多人使用和数据覆盖风险，再完善项目上下文与查找体验。

本方案不引入计费、组织管理、自助注册、聊天系统或通用 AI 助手。MySQL 继续作为持久化真源；IndexedDB 仅保存尚未获得服务端确认的草稿。Keycloak 管理身份，Backend 判断 Workspace 成员与资源权限。

## 2. 现状与差距

| 领域 | 已有能力 | 本方案要补的部分 |
| --- | --- | --- |
| Workspace | `PERSONAL`/`SHARED` 类型、成员角色与权限、成员接口、按 Workspace 隔离 | 共享空间创建接口；切换与成员界面；可安全选择的成员身份 |
| 笔记 | Markdown 编辑、8 秒自动保存、IndexedDB 草稿、服务端 `version` 递增 | 服务端按版本条件更新；冲突时保留草稿并给出处理入口 |
| 项目 | 项目详情聚合关联任务与笔记 | 任务和依据笔记的直接关联；清楚展示项目推进脉络 |
| 查找 | 笔记标题/正文 `LIKE` 搜索，项目和任务标题搜索 | 统一入口、结果上下文与命中展示；按数据规模评估索引 |

当前 `POST /api/workspaces/{workspaceId}/members` 接收调用方传来的 `subjectId`、主体类型和显示资料；`WorkspaceService` 会据此写入主体投影。正式提供成员界面前，应把身份解析移到服务端，防止调用方伪造或覆盖主体资料。现有用户主体只在调用 Workspace 列表时写入本地 `security_principals`，因此“按用户名添加”第一版只能覆盖曾进入系统的用户。

## 3. 实施顺序

### 阶段 A：让多人真正进入同一个 Workspace

**交付范围**

1. 新增创建 `SHARED` Workspace 的接口。创建者成为 `OWNER`；个人 Workspace 仍由首次访问幂等创建。服务端在同一事务中创建空间、成员和审计 Outbox 事件。
2. 在现有 Workspace 列表基础上增加切换入口。用户直接访问有权访问的 `/w/{workspaceId}/...` 时保留该空间选择；失去成员资格后跳转到仍可访问的空间或不可用页。切换时清理当前页面数据，避免短暂展示上一个空间的内容；草稿键继续按用户、Workspace 和笔记隔离。
3. 增加 Workspace 设置页：名称、成员列表、角色变更与移除。按钮显示依赖服务端返回的 `permissions`；所有操作仍由 Backend 授权。保留最后一个 `OWNER` 保护，以及只有 `OWNER` 可以调整 `OWNER` 身份的规则。
4. 为成员选择提供受 `MEMBER_MANAGE` 保护的精确用户名查询，返回服务端已知的用户主体候选；添加成员时由服务端读取主体类型和展示资料。未知用户提示其先登录一次。不要让浏览器直接调用 Keycloak Admin API，也不在前端保存管理员凭证。
5. 评估已发布客户端后调整成员添加契约。推荐新请求只提交 `subjectId` 和 `role`；旧请求字段如需过渡，应由服务端忽略并拒绝与服务端身份不一致的投影，不能继续信任客户端资料。

**主要改动位置**：`openapi/workstation.yaml`、`WorkspaceController`、`WorkspaceService`、`WorkspaceMapper`、`frontend/src/workspace.js`、`frontend/src/router/index.js`、`frontend/src/App.vue`，以及新增设置视图。沿用 TypeScript SDK 与 `frontend/src/api/workstation.ts`，不再建一套前端 DTO。

**验收场景**：两个已登录用户可进入同一共享空间；`VIEWER` 可读不可写；`EDITOR` 不可管理成员；非成员访问空间和跨空间关联按现有隐藏规则处理；移除当前用户后下一次访问不再显示该空间；最后一个 `OWNER` 无法被移除或降级。

### 阶段 B：笔记并发保护与草稿恢复

**服务端规则**

1. 笔记更新请求携带读取时的 `expectedVersion`。在 `NoteMapper` 中使用 `WHERE workspace_id = ? AND id = ? AND version = ?` 条件更新，并原子递增 `version`。以受影响行数判断冲突，不能仅在 Service 读出版本后比较。
2. 更新失败时区分“笔记已删除或不可见”与“版本不匹配”；版本不匹配返回 `409` 和稳定错误码 `NOTE_VERSION_CONFLICT`。冲突事务不修改正文、标签或审计成功事件。
3. 仅在条件更新成功后替换标签。项目删除等现有会递增笔记版本的服务端操作也要纳入并发用例，避免旧页面覆盖其变更。
4. 此改动会使旧客户端的笔记更新请求不再满足契约。发布前明确已发布 Python/TypeScript SDK 的使用范围，并按仓库版本规则升级 OpenAPI 与 SDK；推荐作为下一次破坏性契约版本一起发布。

**前端规则**

1. 用现有 `persistedVersion` 发送 `expectedVersion`；只有收到有效且递增的响应版本后，才更新持久化基准并清除相应草稿。
2. 收到 `409` 时停止该笔记的自动重试，先把当前内容和 `baseVersion` 写入 IndexedDB，再读取服务端版本并展示两份内容。至少提供“复制我的内容”和“以服务端内容重新打开”；用户合并后以最新版本重试。未经用户处理不得覆盖远端。
3. 草稿恢复时比较 `baseVersion` 与服务端版本；不一致则进入同一冲突流程。切换 Workspace、关闭页面或网络中断时，继续按现有草稿策略保存未确认内容。
4. 对保存过程中的再次编辑维持现有排队逻辑，保证发送的快照与版本一一对应；完成响应不能把尚未发送的修改标记为已同步。

**主要改动位置**：`NoteRequest`、`NoteService`、`NoteMapper`、`GlobalExceptionHandler`、OpenAPI、SDK、`NoteEditorView.vue` 和现有草稿存储工具。`notes.version` 已存在，这一阶段原则上不需要新增表或迁移脚本。

**验收场景**：两名成员或两个标签页打开同一笔记，先保存者成功，后保存者收到 `409` 且内容仍可恢复；断网后恢复不会静默覆盖他人更新；标签变更与正文在同一成功事务内生效；新建笔记和单人自动保存保持可用。

### 阶段 C：项目上下文页

以现有项目详情为中心，先做一条最小闭环：项目目标与运行资料 → 依据笔记 → 对应任务 → 完成结果。

1. 在任务上增加可选的“依据笔记”关联；第一版只关联同一 Workspace、同一项目的现有笔记。若一个任务需要多篇依据，再采用独立关联表；不要先在任务描述里解析特殊链接作为数据真源。
2. 项目详情按“资料、任务、相关笔记”组织内容，任务卡片可打开依据笔记，笔记详情能看到关联任务。现有项目聚合接口可扩展所需摘要，但不能把全部 Markdown 正文加载进列表。
3. 展示最近推进信息时先复用现有任务状态与更新时间。审计事件包含操作事实，但不包含可直接展示的业务正文；若需要人工进展说明，再设计独立项目更新实体和权限，不把审计表当内容流。
4. 后续可加入项目笔记模板，如“决策记录”“故障复盘”“运行手册”。模板只预填 Markdown，不建立第二套笔记存储。

**主要改动位置**：任务与项目的 OpenAPI/DTO/Service/Mapper、项目详情与任务界面。若新增关联字段或表，更新 `schema.sql`，并提供对已有数据卷安全、幂等的独立迁移脚本；同一事务内校验两端资源属于当前 Workspace 和项目。

**验收场景**：从项目能找到任务的依据笔记；跨空间或其他项目的笔记不能被关联；删除或取消关联后页面无失效链接；任务列表保持分页且不出现逐条查询笔记的问题。

### 阶段 D：查找体验

先用现有搜索接口实现统一结果页，展示项目、任务和笔记的类型、所属项目、更新时间与可点击目标。笔记正文命中可增加经过安全转义的片段与高亮。记录查询量和响应时间后，再决定是否引入 MySQL 全文索引或专门搜索服务；索引方案要验证中文分词与权限过滤。搜索结果始终由 Backend 限定在当前 Workspace，且不返回列表所不需要的完整正文。

## 4. 依赖、发布与验证

- **顺序**：先确认身份与共享空间创建契约，再完成 Workspace UI；笔记并发保护可在同一阶段独立推进，但应在开放多人编辑前上线；项目上下文依赖稳定的共享使用体验。
- **契约**：所有调用方可见变更先改 `openapi/workstation.yaml`，评估兼容性后生成 Python/TypeScript 客户端并同步版本。手写逻辑仍放在既有 SDK 与前端 API 层，不手改生成文件。
- **数据库**：阶段 A 可复用 `SHARED` 类型和现有表；阶段 B 复用 `notes.version`；阶段 C 若增加持久化关联，必须同时交付初始化 Schema、历史数据迁移、回滚说明和关联完整性测试。
- **安全**：新增接口沿用 Gateway Session/CSRF 与机器 Bearer Token 链路；Backend 独立验证 Workspace 权限。成员搜索只对有管理权限的用户开放，限制精确匹配和返回字段，避免用户枚举。
- **测试**：阶段 A 覆盖共享空间创建、成员查找、角色边界与跨空间访问；阶段 B 覆盖并发更新、冲突码、标签事务和草稿恢复；阶段 C 覆盖关联校验、删除行为和分页查询。按受影响模块运行 `backend` 的 `mvn.cmd verify`、SDK 生成/类型检查与版本检查、`frontend` 的类型检查和构建。前端目前没有自动化测试脚本；关键浏览器交互需做人工双用户与双标签页验证。
- **部署前检查**：在可运行 Docker 的环境完成 Keycloak 登录、Workspace 切换、CSRF 写请求、成员权限和笔记冲突的端到端烟测。已有环境如涉及数据库结构变更，先备份再执行独立迁移；不能依赖重新运行 `schema.sql`。

## 5. 第一批可拆分任务

1. 定稿共享 Workspace 创建、成员查询及身份解析的 API 契约，并确认 SDK 兼容性。
2. 实现共享空间创建与安全成员选择，补齐 Backend 规则及测试。
3. 实现 Workspace 切换和成员设置页，验证直接链接与被移除后的页面状态。
4. 定稿笔记版本请求与 `409` 错误契约，完成服务端条件更新。
5. 实现编辑器冲突处理与草稿恢复，执行双用户、双标签页和断网场景验证。
6. 更新受影响的人类流程文档和 `docs/STATUS.md`，再进入项目上下文页开发。

第一批的完成标准是：两名用户可以在共享空间安全协作，且其中一人的笔记保存不会静默覆盖另一人的修改。
